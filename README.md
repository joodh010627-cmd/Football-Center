# Football Center

어린이 축구교실을 위한 데이터 기반 운영·협업 웹앱 (MVP 프로토타입).

하나의 관계형 데이터 모델 위에 **두 개의 완전히 분리된 인터페이스**를 올렸다.

| | Coach App | Admin Dashboard |
|---|---|---|
| 대상 | 현장 코치 | 대표 |
| 기본 뷰포트 | PC (좌측 레일 + 2단 레이아웃) | PC (1280px 컨테이너) |
| 모바일 | 하단 탭바 + 단일 컬럼 | KPI 2단 + 가로 스크롤 테이블 |
| 목적 | 월 단위 수업 계획 · 3터치 출결 기록 | 커리큘럼 표준화 · 이탈 위험 감시 · 클래스별 마진 관리 |

**세션 라이브러리는 두 역할이 같은 화면을 본다.** 대표는 편집하고, 코치는 같은 화면에서
제안한다 — 코치가 자기 수업의 기준을 요약본으로 본다면 그 요약본이 두 번째 진실이 된다.

두 앱 모두 PC를 기준으로 설계하고 `lg` 브레이크포인트 아래에서 모바일 레이아웃으로 접힌다. 페이지 전체가 스크롤하며 내부 스크롤 컨테이너를 쓰지 않으므로 sticky 액션바가 모든 크기에서 동일하게 동작한다.

핵심 루프는 하나다. **코치가 탭한 데이터가 그대로 대표의 의사결정 지표가 되고, 동시에 학부모 리포트와 코치 개인 포트폴리오가 된다.** 코치는 (커리큘럼에 새 블록을 제안할 때를 빼면) 문장을 단 한 글자도 입력하지 않는다.

그 위의 층은 **세션**이다. 세션은 목표 하나와 그 목표를 위한 훈련 블록들이고, 성장 5각형의 다섯 능력(기술·전술·피지컬·멘탈·태도) 중 하나에 속한다. 코치는 수업 준비에서 오각형의 역량 하나만 누르고, 목표는 앱이 지난 수업과의 연계·오늘 인원·나이대로 골라 제시한다(`recommendGoal`). 마음에 안 들면 `바꾸기`로 고른다. 블록은 그 목표의 기본값이 오늘에 맞춰 따라온다.

예전에는 `트랙 × 나이대 → 주차별 표준 세션`의 커리큘럼이었다. 축구교실은 원생이 매달 바뀌므로 1주차를 들은 아이가 5주차에도 있다는 가정이 성립하지 않고, 그래서 주차 개념을 걷어냈다(`0007`).

```
Ability (5대 능력) ─→ SessionTemplate (목표 한 줄 + 블록 순서) ─→ TrainingBlock
                              ↓ 고르기 = 저장
                        SessionPlan (특정 클래스 · 특정 날짜)
```

세션은 두 곳에서 온다. **표준 라이브러리**(`src/data/sessionLibrary.ts`, id `std-…`, 모든 센터 공통)와 **센터 세션**(DB `session_templates`). 표준 라이브러리는 일반적인 유소년 지도 관행으로 자체 작성한 것이며, 협회 자료가 아니다. 라이선스를 받은 라이브러리가 생기면 같은 자리에 `standard` 행으로 들어간다.

**한 화면에는 핵심 하나만.** 세션 행은 이름만, 목표 문장과 블록은 `더 보기`. 블록은 이름과 분만, 진행법·코칭 포인트·준비물은 탭해서 펼친다.

## 실행

앱은 Supabase 프로젝트 없이 실행되지 않는다. **[docs/SETUP.md](docs/SETUP.md)** 를 먼저 따른다 (약 15분).

```bash
npm install
cp .env.example .env    # URL / anon key 채우기
npm run seed            # 데모 아카데미 + 계정 3개 적재
npm run dev             # http://localhost:5173
```

대표와 코치는 **다른 계정**이다. 화면을 오가려면 로그아웃해야 한다. 역할은 `academy_members.role`에서 오고, 클라이언트에서 바꿀 방법이 없다.

화면 작업용으로는 **개발 서버 전용 미리보기**가 있다: `http://localhost:5173/Football-Center/?preview` (대표) · `?preview=coach` (코치). 로그인 없이 데모 데이터(`scripts/seedData.ts`)를 실제 매퍼에 태워 띄우고, 저장·발송은 하지 않는다. `import.meta.env.DEV` 로 막혀 있어 배포 빌드에는 들어가지 않는다.

```bash
npm run build      # 타입체크 + 프로덕션 번들
npm run typecheck
```

## 기술 스택

- **React 18 + TypeScript + Vite**
- **Supabase** — Postgres + Auth. 테넌트·역할 격리는 전부 RLS가 강제한다
- **Tailwind CSS** — 디자인 토큰을 `tailwind.config.js`에 그대로 매핑
- **lucide-react** 아이콘
- 상태: `useReducer` + Context. 리듀서는 낙관적 업데이트로 남고 그 뒤에 Supabase 쓰기가 붙는다

### 권한 모델

대표 전용 수치는 **컬럼이 아니라 별도 테이블**에 있다.

| 데이터 | 테이블 | 코치가 조회하면 |
|---|---|---|
| 코치 평가점수 | `coach_evaluations` | `[]` |
| 클래스 원가·재등록률 | `class_finances` | `[]` |
| 원생 수강료 | `student_billing` | `[]` |
| 대표의 CS 조치 이력 | `cs_actions` | `[]` |

Supabase는 로그인 사용자 전원이 같은 `authenticated` DB 역할을 쓰므로 컬럼 단위 권한을 줄 수 없고, RLS는 행 단위다. 따라서 **"코치가 못 보는 필드"는 별도 행이어야만 막을 수 있다.** `coaches.satisfaction_score`로 뒀다면 정책으로 가릴 방법이 없었다.

커리큘럼 쓰기는 같은 원리를 반대로 쓴다. 코치의 제안과 대표의 등재는 **같은 테이블의 다른 `status`** 이고, 코치에게는 `insert`만 열되 `with check` 가 `status='pending'` 과 `proposed_by = my_coach_id()` 를 못 박는다. `update` 정책은 **주지 않는다** — 주는 순간 코치가 자기 pending 행을 published로 바꿀 수 있고, 그러면 승인 절차가 UI 장식이 된다.

| 권한 | 코치 | 대표 |
|---|---|---|
| 커리큘럼·표준 세션 읽기 | 등재된 것 + 자기 제안 | 전부 |
| 표준 세션·블록 제안 (`insert`, `status='pending'`) | ✅ | ✅ |
| 자기 제안 철회 (`delete`, pending) | ✅ | ✅ |
| 등재·반려 (`update status`) | ❌ 정책 없음 | ✅ |
| `usage_count` 증가 | `increment_block_usage()` / `increment_template_usage()` RPC만 | ✅ |

같은 이유로 `src/types.ts`에서도 분리돼 있어, 코치 화면 컴포넌트는 평가점수를 **컴파일 자체가 안 된다.**

### 데이터 설계

모든 엔티티는 **중첩 객체 없이 외래키 id만 가진 평평한 행**이다. 조인은 데이터가 아니라 `selectors.ts`에서 일어난다. Firebase/Supabase 테이블로 1:1 이관하기 위한 전제다.

```
Curriculum ──> SessionTemplate ──> blockIds[] ──┐
     ↑                                          ↓
Class ──> curriculumId                    TrainingBlock
  ↑                                             ↑
Student ──┬── classId                    items[].blockId
          └── AttendanceLog ──> sessionPlanId ──> SessionPlan ──> templateId
```

`SessionPlan.items` 는 **순서 있는 배열**이다. `{warmup, skill, game}` 3칸 고정이 아니다.
스킬 두 번, 미니게임 먼저, 웜업 뒤 미니게임만 — 전부 실제로 하는 수업인데 3컬럼
스키마로는 표현할 수가 없었고, 표현 못 하는 스키마는 코치에게 *안 한 수업을 기록하게*
만든다. 마이그레이션 `0005` 가 세 컬럼을 `items jsonb` 로 이관한다.

교체 지점은 `store/AppContext.tsx`의 리듀서 한 곳이다. 각 case 본문을 `await supabase.from(...)` 호출로 바꾸고 현재 로직을 낙관적 업데이트로 남기면 된다. 컴포넌트는 손대지 않는다.

### Mock 데이터

출결 이력은 시드 PRNG(mulberry32)로 생성한다. 매 실행마다 동일한 데이터가 나오고, 원생별 *행동 원형*(`solid` / `steady` / `wobbly` / `fading` / `ghost` / `injured`)에 따라 8주치 출결이 만들어진다.

`lastAttendanceDate`, `status`, `churnScore`는 **손으로 적지 않는다.** 전부 생성된 로그에서 역산된다. 그래서 대시보드의 Red Alert는 언제나 근거를 댈 수 있다.

로스터는 하이브리드다. Red Alert에 실제로 뜨는 22명은 이탈 사유가 담긴 메모와 함께 손으로 작성했고, 나머지는 이름 풀에서 시드 기반으로 생성해 정원을 채운다. 클래스 매출은 하드코딩하지 않고 소속 원생 수강료의 합으로 산출한다.

커리큘럼 트랙은 대표 인터뷰를 옮긴 목업이다. 7개 트랙 × 5개 나이대 격자는 **일부러 비어 있다** — 킨더는 U7에만, 엘리트는 U15에만, 주말 클럽은 U9·U11에만 있다. 35칸을 다 채운 격자는 어느 센터도 실제로 가르치지 않는 허구다.

원생 104명 · 클래스 12개 · 코치 7명 · 커리큘럼 8트랙 · 표준 세션 33개(+ 승인 대기 2개) · 훈련 블록 21개(+ 대기 1개) · 행동 태그 21종 · 출결 로그 약 1,900건 · 수업 설계 약 300건.
월 매출 약 2,919만원 / 공헌이익 약 1,100만원 규모.

시드 불변식은 `scripts/seedData.test.ts`가 지킨다 — 데모는 픽스처가 아니라 영업 화면이므로, 달력이 잘못 생성되면 깨진 테스트가 아니라 깨진 미팅이다.

## Phase 1 구현 범위

### 1. 세션 라이브러리

`클럽 → 세션 라이브러리`. 다섯 능력 칩으로 거르고, 행을 열면 목표와 블록이 보인다. 대표는 센터 세션을 만들고 코치의 제안을 승인한다(`더 보기 → 승인 대기`). 코치는 제안만 한다.

- 제안 행과 등재 행은 **같은 테이블**에 산다. `status` 하나만 다르므로 대표의 승인 큐는 별도 스키마가 아니라 필터다.
- RLS가 코치의 `insert`를 `status='pending'` 으로 못 박고, 코치에게는 `update` 정책을 **주지 않는다.** 그래서 코치는 자기 제안을 철회만 할 수 있고 고칠 수는 없다.
- 승인 대기 수업·블록은 수업 준비에 오르지 않는다.
- 수업 준비의 목표 목록은 반의 연령에 맞는 것만, **반의 커리큘럼 먼저 · 최근 진행한 목표는 아래로**, 그 안에서 센터 → 표준, 사용 빈도순이다.

### 2. 수업 — 코치가 원래 준비하던 순서대로

용어: **클럽** = 센터 전체, **클래스** = 코치가 맡은 반, **수업** = 특정 날짜의 한 번, **훈련 블록** = 수업 안의 훈련 하나. 코드의 `SessionTemplate`은 화면에서 "목표"(라이브러리에서는 "수업")다.

하단 가운데 탭이 `수업`이다. 첫 화면은 그날의 대시보드: 큰 날짜, 수업이 둘 이상이면 시작 시각 줄(시간표 겸 이동), 그 아래 스와이프하는 수업 카드. 카드는 `준비 → 수업 → 기록` 세 칸 막대로 진행 상태를 보여 주고, 버튼은 상태에 따라 하나다: `수업 준비` → `수업 보기` → `수업 기록`. 아래 띠에는 오늘의 칼럼과 브랜드 스토리만 둔다.

- **수업 준비**(`LessonPrepScreen`): ① 오늘 오는 선수(인원·체험, 명단은 접힘) ② 지난 수업(날짜·목표·출석·그날 남긴 태그, 그 전 두 번은 한 줄씩) ③ 오늘의 목표(다섯 능력 중 포커스 → 목표 하나). 목표를 누르면 훈련 블록이 **오늘에 맞춰 자동 구성**된다(`src/data/lessonPrep.ts`):
  - 연령에 안 맞거나 인원(`N대M`, `N:M`에서 읽는다)보다 많은 선수가 필요한 블록은 같은 능력·같은 자리의 블록으로 바꾼다.
  - 시간은 5분 단위로 반의 수업 시간에 맞춘다. 늘릴 때는 게임부터, 줄일 때는 가장 긴 훈련부터(게임은 마지막).
  - 바꾼 점은 `N명 · N분 · U7에 맞춰 짰어요` 아래 한 줄씩 보인다.
- 블록은 탭하면 진행법·코칭 포인트·준비물, 그 아래 시간 ±5분·위/아래, 그리고 글자가 붙은 `내용 수정`·`다른 블록`·`빼기`. `다른 블록`은 그 블록의 능력으로 라이브러리를 열고, 새 블록은 원래 자리의 시간을 물려받는다. 블록을 고쳐도 목표 링크는 유지된다.
- **내용 수정**은 이 수업에만 적용된다. 이름·진행 방법·코칭 포인트 중 라이브러리와 달라진 것만 `SessionItem.edit`로 계획의 jsonb에 함께 저장되므로 마이그레이션이 필요 없고, 라이브러리가 나중에 바뀌어도 그날 실제로 한 내용이 남는다. `원래대로`는 edit를 지운다. 수업 화면과 학부모 리포트는 고친 이름을 쓴다(`blockAsRun`).
- 색은 그린 하나다. 진행 막대는 밝기로 단계를 말한다 — 짙은 초록 = 끝남, 밝은 초록 = 지금 할 일(수업 중엔 깜빡임), 옅은 초록 = 남음. 기록 대기도 따로 색을 바꾸지 않는다.
- 이미 준비한 수업을 열면 저장된 목표와 블록 그대로 열리고, 다른 목표를 고르면 다시 구성한다.
- 사용된 블록은 `usageCount`가 올라가 다음 정렬이 된다(센터 블록만 — 표준 블록의 카운터는 DB에 없다).

### 3. 일정 — 월간 달력

월 격자에 날짜마다 일정 점(최대 3개, 기록 안 된 수업이 있으면 첫 점이 주황), 아래에 고른 날의 수업·체험 목록. 목록의 버튼은 `준비`(목표 미정) / `기록` / 상태. 클래스 페이지는 수업 화면의 클래스 이름을 누르면 열리고, 다음 수업과 지난 수업 목록을 보여 준다.

### 4. 수업 기록 — 한 화면, 한 버튼

- **전원 출석으로 시작한다.** 정상적인 수업이면 `완료` 한 번. 코치는 예외만 건드린다.
- 학생 카드 우측 상태 버튼 탭 = `출석 → 결석 → 부상` 순환. 좌측 색상 스트립이 신호등 역할을 한다.
- 모바일에서는 카드 본문을 탭하면 **행동 태그 칩이 카드 안에서 인라인으로 펼쳐진다.** 바텀시트도 모달도 쓰지 않는다. PC에서는 우측 고정 패널에 칩이 뜬다 — 그리드에서 카드를 펼치면 명단 전체가 리플로우되기 때문이다. 두 경우 모두 태깅 중 명단을 놓치지 않는다.
- 태그는 기술/태도/팀워크/피지컬/주의 5개 레일로 나뉜 21종 프리셋. 자유 입력은 없다.
- 결석·부상 처리된 원생의 태그는 자동으로 비운다. 오지 않은 학생의 경기력 기록은 성립하지 않는다.
- **[완료]** 한 번으로 저장된다. 학부모 알림은 저장 뒤에 따로 누르는 선택 단계(`학부모 알림`)다 — 수업을 끝내는 일이 메시지 발송을 기다리지 않는다. 발송될 문면은 탭한 데이터만으로 조립된다.

### 5. Admin Dashboard

**Churn Risk Alert Engine** (`data/churn.ts`) — 가중치 합 100의 4개 축.

| 축 | 가중 | 포화 기준 |
|---|---|---|
| 최근 출석 공백 | 45 | 14일 |
| 30일 결석률 | 30 | 50% |
| 학부모 피드백 지연 | 15 | 21일 |
| 등록 초기 취약성 | 10 | 180일 |

55점 이상이 Red Alert, 78점 이상이 `즉시 조치`. 30일 이상 미출석은 위험군이 아니라 `휴원`으로 분류한다.

점수는 항상 **근거 문장과 함께** 표시된다 ("21일째 미출석 (2주 초과)", "학부모 피드백 34일 지연"). 대표가 숫자를 의심하지 않고 바로 전화를 걸 수 있어야 하기 때문이다.

`[CS 조치 완료]`를 누르면 `CsAction`이 기록되고 큐에서 빠지며, 학부모 접촉일이 갱신되어 점수에 즉시 반영된다.

**Class Retention & Margin Table** — 공헌이익 기준 정렬. 재등록률 80% 미만은 적색, 마진율 25% 미만은 경고색으로 뜬다. 정원 충족률·출석률·코치 만족도를 한 행에서 비교한다.

**KPI 타일 = 점프 링크** — 상단 6개 지표는 각각 그 숫자를 설명하는 섹션으로 스크롤한다. 재원생 → 원생 명단, 이탈 위험군 → Red Alert, 월 매출·재등록률 → 클래스 테이블, 출석률 → 기록 피드, 기록 충실도 → 커리큘럼 준수율.

**원생 명단** — 100명 규모에서는 알림 큐만으로 부족하다. 상태 칩과 클래스 필터로 좁히고 이탈 위험도 높은 순으로 정렬한다.

**부수 패널** — 코치별 커리큘럼 준수율(품질 통제), 현장 기록 피드(프로세스 준수 증거), 원생 성장 리포트 모달(출결 스트립 + 태그 누적 + 코멘트 이력).

준수율은 **두 숫자로 본다.** `표준 세션 준수율`(목표 70%)은 코치가 설계한 수업이 그 반 커리큘럼에 등재된 표준 세션이었는지를 묻고, 괄호 안의 `표준 블록 사용률`(목표 60%)은 쓴 블록 중 표준으로 표시된 비율을 묻는다. 후자만 보면 서로 무관한 세 트랙에서 표준 블록을 하나씩 뽑아 온 코치가 만점을 받는다 — 전자가 바로 그 드리프트를 잡는다.

## 설계 판단 몇 가지

**출석률에서 부상은 제외한다.** 부상을 결석으로 세면 정직하게 기록한 코치가 지표에서 손해를 본다. 그러면 코치는 전원 출석으로 찍기 시작하고 데이터는 죽는다.

**같은 날 재제출은 덮어쓴다.** 중복 집계 대신 갱신이다.

**제출 후에도 draft를 유지한다.** 알림톡 모달이 명단 위에 뜨는데, 여기서 draft를 비우면 모달 아래 화면이 언마운트된다.

**기록 충실도를 KPI로 올렸다.** 태그·코멘트가 붙은 로그의 비율이다. 이 숫자가 떨어지면 대시보드의 다른 모든 숫자를 믿을 수 없다는 뜻이다.

**수업 설계와 출결은 탭이 아니다.** 예전에는 둘 다 레일의 탭이었고, 클래스를 고르기 전에는 disabled였다. 상태 표현은 정직했지만 구조가 틀렸다 — 그 둘은 *가는 곳*이 아니라 클래스 안의 *단계*다. 레일에서 빼고 나서야 달력이 네 번째 탭이 아니라 앱의 척추가 되었다.

**미래를 전부 등록해 두지 않는다.** 시드는 각 클래스의 다음 두 번만 `등록`으로 채우고 나머지는 행을 만들지 않는다. 달력의 존재 이유가 "아직 아무도 설계하지 않은 수업"을 드러내는 것인데, 미래가 전부 칠해져 있으면 그 상태를 볼 수가 없다.

**한 클래스의 한 날짜에 설계는 하나다** (`session_plans` 고유 인덱스). 달력 칸이 두 개의 설계를 가리키면 "등록됨"이 무슨 뜻인지 말할 수 없다. 재설계는 같은 행을 덮어쓰므로, 그 행을 참조하는 출결 로그도 계속 유효하다.

## 알려진 한계

- 재등록률은 `class_finances`의 고정값이다. 실제로는 결제 이력(`payments`)에서 산출해야 한다.
- 알림톡은 시뮬레이션이다. 실제 발송 연동 없음.
- **`parent_phone`이 평문이다.** 운영 전 암호화가 필요하다.
- **`audit_logs` 테이블과 정책은 있으나 앱이 아직 쓰지 않는다.** 열람 기록이 남지 않는다.
- 코치 초대 코드 발급 UI가 없다. 현재는 SQL로 발급한다 (`docs/SETUP.md` 참조).
- **이탈 엔진이 주 2~3회 수업을 가정한다.** 주 1회 클래스에서는 정상 원생이 위험군으로 뜬다 (`docs/PRODUCTIZATION.md` §2-1).
