제품화 계획서 §5-B3 **1단계** 산출물.
목적은 두 가지다.

1. **영업 도구** — "이 양식으로 주시면 10분 안에 올려드립니다"
2. **조사 도구** — 대표 엑셀이 이 양식과 어긋나는 지점이 곧 현장 조사 결과다

관련 파일
- 배포용 양식: `docs/templates/FC_원생명단_양식_v1.xlsx`

## 0. 설계 원칙

**필수 컬럼은 4개뿐이다.** 이름 · 클래스 · 보호자연락처 · 월수강료.
이 4개만 있으면 임포트가 성립하고 Day-1 대시보드가 전부 그려진다.
나머지는 채울수록 화면이 살아나는 구조지, 없다고 막히지 않는다.

미팅 자리에서 "이거 없는데요"가 나오는 순간 데모가 끊긴다. 그래서 진입 장벽을 4개로 깎았다.

**계산되는 값은 임포트하지 않는다.** 아래는 양식에 **없어야** 하고, 있어도 무시한다.

| 무시 | 이유 |
|---|---|
| 상태 (정상/위험/휴원) | `churn.ts`가 산출 |
| 이탈위험도 | 〃 |
| 출석률 · 재등록률 | 출결/납부 이력에서 역산 |
| 공헌이익 · 마진율 | `selectors.ts`가 산출 |

> 영업 문장: **"이건 안 적으셔도 됩니다. 시스템이 계산합니다."**
> 대표가 매달 손으로 채우던 칸이 사라지는 게 눈에 보이는 순간이다.

## 1. 시트 1 — `원생명단` (필수)

| 열 | 컬럼명 | 등급 | 타입 | 규칙 |
|---|---|---|---|---|
| A | 이름 | **필수** | 문자 | 1~20자 |
| B | 클래스 | **필수** | 문자 | 시트2와 대조. 없으면 자동 생성 |
| C | 보호자연락처 | **필수** | 문자 | `010-0000-0000`. 숫자만 입력해도 정규화 |
| D | 월수강료 | **필수** | 정수 | 원(KRW). `150,000` `15만원` 파싱 |
| E | 등록일 | 권장 | 날짜 | `YYYY-MM-DD` |
| F | 생년월일 | 권장 | 날짜 | `YYYY-MM-DD` → 연령대 자동 산출 |
| G | 연령대 | 선택 | 목록 | `U7·U9·U11·U13·U15`. 비우면 F에서 산출 |
| H | 보호자성명 | 선택 | 문자 | |
| I | 최근출석일 | 선택 | 날짜 | **비어 있는 것이 정상** (§5) |
| J | 메모 | 선택 | 문자 | |
| K~ | `2026-06` `2026-07` … | 선택 | 납부 | 월별 납부 그리드 (§4) |

### 연령대 산출 규칙 (기본값 · 팀별 조정 가능)

`등록일` 기준 만 나이로 계산한다.

| 만 나이 | 연령대 |
|---|---|
| ~7세 | U7 |
| 8~9세 | U9 |
| 10~11세 | U11 |
| 12~13세 | U13 |
| 14세~ | U15 |

> ⚠️ **검증 필요한 가정.** 국제 U-시스템은 출생 연도 기준이고, 국내 축구교실은
> **학년 기준**(초1·초2…)으로 반을 나누는 경우가 흔하다. 첫 미팅에서 반드시 확인할 것.
> `G열`을 직접 입력하면 F열 산출보다 **우선**하므로, 규칙이 안 맞는 팀도 막히지는 않는다.
> 최종적으로는 `academy_settings.age_groups`로 팀별 설정한다.

| 장소 | 선택 | 문자 | |

메타데이터는 비워둔다. 다만 아래 §3 때문에 **`수업요일`만은 받아내는 게 좋다.**

## 3. `수업요일`이 필요한 진짜 이유

`src/data/churn.ts:52`의 이탈 점수는 **"14일 미출석 = 위험 포화"** 로 고정돼 있다.
이건 수업 주기를 암묵적으로 가정한 값이다.

| 클래스 주기 | 14일 = | 판정 |
|---|---|---|
| 주 3회 | 6회 결석 | 심각 — 맞음 |
| 주 2회 | 4회 결석 | 위험 — 맞음 |
| **주 1회** | **2회 결석** | **감기 한 번. 정상인데 경보** |

주 1회 클래스를 운영하는 팀에서 **정상 원생이 무더기로 Red Alert에 뜬다.**
대표가 헛전화를 두 번 걸면 그 뒤로 알림을 안 본다.

→ 기준을 "일수"가 아니라 **"놓친 세션 수"** 로 바꿔야 하고, 그 입력이 `수업요일`이다.
이 수정은 1단계 다음 작업으로 예정돼 있다.

## 4. 납부 그리드 (선택)

국내 소상공인 엑셀은 납부를 **월별 가로 컬럼**으로 관리하는 경우가 많다.
그 습관을 고치라고 하지 말고 그대로 읽는다.

> ⚠️ **가설.** 실제 파일을 아직 못 봤다. 첫 미팅에서 검증한다.

### 인식하는 헤더 형태

```
2026-06   2026.06   2026/06   26년 6월   6월   '26 6월
```

### 셀 값 해석

| 값 | 해석 |
|---|---|
| `O` `○` `●` `V` `✓` `완납` | 납부 |
| `X` `x` `✗` `미납` | 미납 |
| 날짜 (`6/15`, `2026-06-15`) | 해당일 납부 |
| 숫자 (`150000`) | 해당 금액 납부 |
| 빈칸 | **등록일 이후면 미납, 이전이면 무시** |

마지막 규칙이 중요하다. 3월에 등록한 원생의 1~2월 칸이 비어 있는 건 미납이 아니다.
이걸 구분 못 하면 미납 화면이 첫 화면부터 거짓말을 한다.

→ 세로로 펴서 `payments` 행으로 변환한다 (계획서 §3-2).

## 5. `최근출석일`은 비어 있는 게 정상이다

대부분의 축구교실은 출결을 카톡·종이·코치 머릿속에 둔다. 엑셀에 없다.
**그래서 이 칸은 비워둔 채 임포트되는 것이 기본 경로다.**

이때 절대 하지 말아야 할 두 가지:

| 하지 말 것 | 결과 |
|---|---|
| 등록일로 채우기 | `churn.ts:105`의 30일 규칙에 걸려 **전원 "휴원"** |
| 오늘 날짜로 채우기 | 사실이 아닌 데이터 생성. **전원 "정상"** |

**정답은 세 번째 상태다.** `Student.lastAttendanceDate`를 nullable로 바꾸고,
이력이 없으면 점수 대신 **"산출 불가 · 기록 3주 후 활성화"** 를 반환한다.
숫자를 지어내느니 정직하게 비워두는 쪽이 데모에서도 강하다.

> 영업 문장: **"오늘 올리시면 매출·미납·정원이 바로 보이고,
> 3주 기록하시면 이탈 경보가 켜집니다."**
> 계속 써야 할 이유까지 같이 파는 문장이다.

## 6. 시노님 사전 — **이것이 "객관식"의 본체**

임포터는 헤더명을 아래 사전으로 자동 추론하고, **못 맞춘 컬럼만** 드롭다운으로 되묻는다.
정규화(공백·괄호·특수문자 제거, 소문자화) 후 비교한다.

| 정규 필드 | 인식하는 표기 |
|---|---|
| `name` | 이름, 성명, 원생명, 학생명, 선수명, 아동명, 회원명 |
| `className` | 클래스, 반, 반명, 클래스명, 소속, 소속반, 팀, 그룹, 요일반 |
| `parentPhone` | 연락처, 전화번호, 휴대폰, 핸드폰, HP, 학부모연락처, 보호자연락처, 보호자전화, 모연락처, 부연락처, 비상연락처 |
| `monthlyFee` | 월수강료, 수강료, 회비, 월회비, 교육비, 금액, 납부액, 월납입액 |
| `enrolledAt` | 등록일, 가입일, 시작일, 입회일, 등록날짜, 최초등록일 |
| `birthDate` | 생년월일, 생일, 출생일, 생년월 |
| `ageGroup` | 연령대, 연령, 나이대, 카테고리, 학년\* |
| `parentName` | 보호자성명, 보호자명, 학부모명, 보호자, 부모님성함 |
| `lastAttendanceDate` | 최근출석일, 최종출석일, 마지막출석 |
| `memo` | 메모, 비고, 특이사항, 참고, 기타 |

\* `학년`은 값 변환이 필요한 특수 케이스다 (`초3` → 만 9세 → U9).
국내에서 흔한 분류라 반드시 지원해야 하지만, 학년→나이 매핑도 §1의 가정에 의존한다.

**이 표는 미팅마다 자란다.** 못 맞춘 컬럼이 나오면 그 자리에서 받아 적고 사전에 추가한다.
그게 이 단계의 진짜 목적이다.

## 8. 개인정보 — 임포터가 지켜야 할 선

미팅 자리에서 **남의 아이 이름과 부모 전화번호**를 노트북에 올리는 일이다.
기술 문제이기 전에 신뢰 문제이므로 아래를 제품이 강제한다.

1. **주민등록번호를 받지 않는다.** 헤더에 `주민`·`주민번호`·`주민등록번호`가 있으면
   해당 컬럼을 버리는 게 아니라 **파일을 거부하고** 제거 후 재업로드를 요청한다.
   생년월일이 필요하면 `생년월일` 컬럼으로 따로 받는다.
2. **브라우저를 벗어나지 않는다.** 영업용 프로토타입은 파싱·저장·표시가 전부 로컬이다.
   서버 전송 없음.
3. **[전체 삭제] 버튼을 항상 노출한다.** 미팅이 끝나면 그 자리에서 눌러 보인다.
4. **소리 내어 말한다.** — *"이건 대표님 브라우저 안에서만 돕니다.
   서버로 안 갑니다. 지금 지워 드릴게요."*
   방어가 아니라 영업이다. 대부분의 축구교실은 지금 카톡방+엑셀로 관리 중이라
   이 말이 곧 차별점이 된다.

> 정식 계약 시에는 서버로 이관하며, 그때 `consents` 테이블과 법정대리인 동의 절차가
> 함께 들어간다 (계획서 §3-2, §6).

## 9. 영업용 프로토타입의 한계 — 명확히 선을 긋는다

- 브라우저 메모리 + localStorage에만 저장된다. **실제 운영에 쓰면 안 된다.**
- 미팅 중 새로고침으로 데이터가 날아가지 않도록 localStorage 저장은 필수.
- 대표에게 반드시 말할 것: **"지금은 시연용입니다. 계약하시면 서버로 옮깁니다."**
- **대표의 실제 원생으로 가짜 출결 이력을 만들지 않는다.**
  화면은 화려해지지만 "우리 애가 지난주 결석했었나?" 한 번 대조하면 끝난다.
  욕망을 만드는 화면은 **별도의 시드 데모 팀**으로 보여주고, 라벨을 명확히 단다.
