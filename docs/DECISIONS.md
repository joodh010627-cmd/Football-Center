# 기획 논의와 결정 기록

FC GROWTH 앱을 만들면서 내린 기획 판단을 모아 둔 문서입니다. 무엇을 만들었는지보다 **왜 그렇게 정했는지**를 남깁니다.
새 결정이 생기면 맨 아래 "결정 이력"에 날짜와 함께 추가합니다.

## 1. 개발 철학

- **핵심만 남긴 단순함.** 한 화면의 정보량을 줄인다. 한 화면에는 지금 할 일 하나만 크게 보인다.
- **선택으로 기능을 쓴다.** 자주 쓰는 경우는 칩·버튼으로 고르게 하고, 더 많은 자유가 필요할 때만 텍스트로 직접 쓰게 한다.
  - 예: 설문 질문은 `질문 : A / B` 한 줄 문법, `(복수)`, `B!`(상담 필요 표시).
- **표현은 짧고 평범하게.** 어색한 문장, 꾸민 말투를 쓰지 않는다.
  - 쓰지 않는 표현: "문의부터 첫 달까지, 한 가족씩", "전화할 집", "답이 없는 집", "~할 차례예요", "집".

## 2. 서비스 핵심 흐름

1. **수업 기록 → 감독 지표 → 학부모 리포트.** 코치가 수업에서 탭 몇 번으로 기록하면 감독에게 지표가 쌓이고 학부모에게 리포트가 간다. 다른 학원 관리 앱과 구분되는 축이다.
2. **신규 회원 온보딩이 가장 중요하다.** 이 업종은 들어오고 나가는 아이가 많아서 첫 4주를 잘 넘기느냐가 매출을 좌우한다. 그래서 폼 탭의 중심을 온보딩에 둔다.

## 3. 폼 탭 (신규 문의)

### 구조
- 탭 이름은 **폼**, 화면 제목은 **신규 문의**.
- 단계: **문의 → 체험 → 등록 → 신규 원생**.
  - 이름 변경: "새로운 만남" → **신규 문의**, "첫 달" → **신규 원생**.
- 첫 화면은 **오늘 할 일**만 보인다. 칩을 눌러 한 가족씩 넘기는 카드(수업 탭과 같은 토글 방식).
  - 오늘 체험·첫 수업이 있는 아이가 먼저, 그다음 연락할 가족.
  - 카드에는 이름, 할 일, 이유, 단계 막대, 전화 버튼만.
- 그 아래: 단계별 현황, 안내 보내기(체험 초대 / 참가 신청 / 동의·조사 / 의견 듣기), 보낸 안내.
- "Today" 박스는 없앴다. 감독·코치에게 중요한 건 날짜 표시가 아니라 **오늘 누구에게 무엇을 해야 하는지**다.

### 할 일 엔진
- 상태를 따로 저장하지 않고 기록에서 계산한다(`src/data/onboarding.ts`).
- 통화 단계: 첫 상담 전화 → 체험 후 통화 → 환영 안내 → 1주 차 통화 → 4주 차 통화.
- 통화 결과: 완료 / 부재중(다음 날 다시) / 보류·상담 필요(3일 뒤 다시).
- 신규 원생은 등록 후 45일 안의 아이만 대상. 기존 명단을 가져온 아이는 제외된다(의도된 동작).

### 설문을 쓸 때와 전화할 때
- **설문**: 여러 가족에게 같은 질문을 할 때 — 참석 확인, 일정 조율, 동의, 재등록, 만족도, 주문, 참가 신청.
- **전화**: 고민·불만·결정이 걸린 대화 — 첫 상담, 체험 후, 1주·4주 차, 그리고 설문에서 "상담 필요"로 표시된 답.
- 설문 답 중 고민이 보이는 선택지(`!`)는 자동으로 "상담 필요"로 올라와 전화로 넘어간다.
- 학부모는 계정 없이 알림톡 링크(`?s=`)로 답한다.

## 4. 디자인 기준 (수업 탭 기준)

- 작은 초록 한글 라벨 + 큰 제목. 영어 대문자 라벨을 쓰지 않는다.
- 화면당 메인 카드 하나(`.mesh`), 칩 토글 + 옆으로 넘기는 카드.
- 단계 막대는 초록 밝기로만 구분(완료 / 현재 / 남음).
- 버튼은 알약 모양, 목록은 흰 카드에 줄로 나눈다, 부가 정보는 "더 보기"로 접는다.
- **초록 단색.** 노랑·주황 같은 따뜻한 색은 쓰지 않는다.
- 공용 부품은 `src/components/forms/ui.tsx`.

2026-09-30, 클라우드 세션에서 배포하면서 PC에만 있던 9/28 작업을 덮어쓴 사고가 있었다. 그 뒤로 정한 규칙:

- 배포 전에 실서비스 번들과 GitHub main이 같은지 확인하고, 화면 캡처를 먼저 보여 준다.
- PC에서 작업하기 전에 `git pull`, 클라우드 세션을 쓰기 전에 PC에서 `git push`.
- DB 마이그레이션 SQL은 앱 미리보기(100줄에서 잘림) 대신 **GitHub raw 링크**에서 복사한다. 적용 순서는 0006 → 0007 → 0008 → 0009, 끝에 `notify pgrst, 'reload schema';`.

## 6. 2026-10-07 점검

결론: **방향은 맞다.** 가장 큰 위험은 기능이 아니라 실제로 쓰는 학원이 아직 없다는 점이다.

### 놓치고 있는 부분 (중요한 순서)
1. **실사용 학원 없음.** PRODUCTIZATION의 원래 계획은 "명단 가져오기까지 만들고 판다"였다. 사용 기록도 없어 시범 학원이 생겨도 실제로 쓰는지 알 수 없다.
2. **알림톡이 실제로 나가지 않음.** 코드와 대기열은 준비됐지만 카카오 채널·발송 업체가 연결되지 않았다.
3. **수납 없음.** 미납 확인이 감독의 핵심 업무인데 앱에 없다. 재등록률도 고정값이다.
4. **개인정보.** `consents` 테이블을 앱에서 안 쓴다. 보호자 번호가 평문. `audit_logs` 미사용.
5. **코치 초대 화면 없음.** DB에는 `create_coach_invite`가 있지만 버튼이 없다.
6. **기존 원생은 신규 원생 관리에서 빠짐.** 처음 보는 사용자에게 빈 화면으로 보일 수 있다.

### 작업 방식의 위험
- PC와 클라우드 두 곳에서 배포 가능하고 자동 배포·테스트 서버가 없다 → 장기적으로 "main만 자동 배포".
- 마이그레이션을 붙여 넣는 방식이라 실수 위험이 크다.
- 백업과 오류 알림이 없다.

### 작은 불일치
- 클럽·일정 탭이 예전 스타일(노란 배지, 빨간 경고, 영어 "Owner/Coach").
- 문서가 낡음: README 첫 표(앱 두 개 설명), "이탈 위험은 주 1회 기준" 한계(이미 수업 횟수 기준으로 바뀜), PRODUCTIZATION 일정.

### 제안한 우선순위
1. 지금 상태 정리 — 0006~0009 적용 확인, 예시 데이터 버그 수정(8339ff5) 배포.
2. 시범 학원 1곳 — 코치 초대 화면, 알림톡 실제 연결, 등록 시 보호자 동의.
3. 사용 기록 — 코치가 수업 탭을 매일 여는지, 감독이 폼 탭에서 전화하는지.
4. 수납 — 시범 학원에서 필요하다는 말이 나올 때.
5. 클럽·일정 탭 디자인 통일, 문서 정리.
